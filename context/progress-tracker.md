| 2026-09-21 | The unit vector is one bracketed value, not three rows | It is read as a direction rather than three separate quantities, and three more rows would undo what the two columns buy. |
| 2026-09-21 | The card header is laid out apart from the table of numbers | Found by the user: the angles sat far from their values. Both shared one grid, so the stretch that pushes the delete button to the right edge was also stretching what had become the right-hand label column. The header is now its own row above the grid, and the slack sits in a spacer between the two column pairs rather than inside either. |
| 2026-09-21 | The right column's values are left-aligned while the left column's are right-aligned | Not an oversight. The unit vector is about three times the width of an angle, so right-aligning that column would size it to the unit vector and strand every angle away from its own name - the same fault in miniature. Angles are all the same width and line up either way; the left column's values are not, so they keep their decimal points aligned. |

| 2026-09-21 | The edit form commits on **Apply** or Enter, not on every keystroke | F-08 says changes apply "immediately", which is read as "the instant Apply is pressed, with no confirmation step" rather than per character. Per-keystroke editing makes every intermediate state a real change - typing "-3" moves the vector twice - and would give G2.8 one undo step per character. It also keeps G1.3's rule that a half-typed `-` or `3.` is never an error. |
| 2026-09-21 | Editing lives in its own box, not as a mode on the create form | The same filled-in fields meaning two different things depending on a control the student may not be looking at is how an eleventh vector gets created by someone who meant to change one. The cost, a second set of fields, was paid off by extracting `VectorForm`, so the toggle and the parse dispatch exist once. |
| 2026-09-21 | The edit fields hold two decimals, the same as the info panel, and so Apply can round the stored value | The form sits beside a card showing the same vector, and a field reading `6.123233995736766e-17` says nothing a student can use. This is the one place displayed text feeds back into the maths, against `interaction-spec.md` section 2.2; what it rounds away is dust from the angle conversion, never a value anyone typed. Raised with the user before building and accepted. |
| 2026-09-21 | φ shows `0.00` with a note on the z axis, rather than the em dash the info panel uses | Section 2.3 calls φ undefined there and section 2.5 says to print an em dash, but an em dash cannot be read back when Apply is pressed, and an empty field would make the form arrive already failing its own validation. A typed φ is genuinely irrelevant on the z axis, so zero changes nothing. |
| 2026-09-21 | The edit fields are refilled only when the vector they show has changed | Every action notifies every listener, so refilling on each event would wipe half-typed text whenever an unrelated card was ticked. The form remembers the name and components it was filled from and compares. Refilling only on a change of *letter* was rejected: from G5 a hand-steered vector would leave stale numbers that Apply would silently put back. |
| 2026-09-21 | `to_spherical` takes θ from `direction_angles` instead of computing it | θ measured from +z and the direction angle γ are the same angle. Reusing it avoids a second copy of the clamp that stops `acos` raising `ValueError` for a vector lying on an axis - the exact duplication the G2.1 clamp decision warned about. |
| 2026-09-21 | A locked vector is refused in `actions.edit_vector`, not only by the greyed form | F-08 asks only for the disabled form, but `architecture.md` section 2 puts every change through the actions, and in G5 the gesture engine calls this same function. A rule kept in the widget would have to be written a second time there, and could be forgotten. |
| 2026-09-21 | The vertical splitter between the two panels was replaced by a layout | Necessary for the foldable boxes, not cosmetic: a `QSplitter` hands out the sizes it was last given and never re-reads a child's needs, so folding a form freed nothing - the box shrank and left the gap as padding. A layout gives the action panel the height of its forms and the vector list all the rest, which is the only thing the splitter handle was ever dragged to do. |
| 2026-09-21 | The mode radios stay stacked, against the compacting done everywhere else | Measured: two radios fit one 300px row only as "x, y, z" and "r, θ, φ" (230px against 260px usable); every wording that keeps "Components (x, y, z)" and "Magnitude + angles" needs 326-518px. F-04's criterion names those two modes, and shortening them to buy 24px would have quietly weakened a ticked criterion. |
| 2026-09-21 | Conversion between the two modes on toggling was **not** built | A G1.3 comment promised it for G2.4, but F-08's criteria do not ask for it and it was not in the approved plan. In the edit box it costs nothing, because both sets of fields are filled from the vector whenever it changes. The stale comment was corrected rather than left as a false promise. Open: offered to the user, not yet chosen. |

| 2026-09-21 | The lock control sits on every card, not only on locked ones, reversing the G2.3 decision | That decision was made when nothing could set the flag, so an indicator was all it could be. A control that only appears once the state is already set cannot be used to reach that state, and the alternative - locking from the action panel, reading the result in the info panel - splits one idea across two places and makes unlocking require activating the vector first. |
| 2026-09-21 | The lock control is the word Lock / Locked, not a padlock glyph | Built first with 🔒 and 🔓, and the user could not tell them apart. Windows draws emoji as colour bitmaps, so they ignore the colour and weight that were carrying the difference. Text obeys both, and reads the same whatever font the machine has. "Locked" is a state in bold accent blue; "Lock" is an offer in muted grey. |
| 2026-09-21 | A locked vector's delete button is greyed with an explaining tooltip, rather than removed or left to fail | Removing it makes the header shift as vectors are locked and reads as a lost feature; letting it fail puts an error in front of someone for doing something reasonable. Greyed matches how the edit form already treats a locked vector, so locking looks like one rule rather than three. |
| 2026-09-21 | `delete_vector` refuses a locked vector, but `clear_all` does not | F-09a protects a vector from being deleted on its own; F-10 promises that clearing the scene takes locked vectors too, and the prompt has said so since G1.5. The two are different questions and a test asserts the prompt's wording. |

| 2026-09-21 | Only one vector shows its components at a time, and the store holds the name rather than a set | The user's call, made after seeing three vectors resolved at once. Every vector resolves onto the same three axes, so two at once puts two arrows of the same colour on the same line and crowds their labels into the same corner. Holding `str \| None` makes it structural: there is no state in which two are shown. F-13a says "toggled per vector", which this still is, and it matches `interaction-spec.md` section 7, where `Victory` toggles components on the active vector. |
| 2026-09-21 | Component arrow thickness is worked out from the vector's magnitude, not from each component's own length | The first version was invisible, which the user reported. A component is shorter than its vector, so scaling its radius by its own length made it thinner than the axis line it lies on, and it read as part of the axis. One thickness for all three also lets them be compared. |
| 2026-09-21 | The component arrows are held back by flat shading and transparency rather than by being thin | Made thick enough to see, they looked more important than the vector itself - the user's second report. F-13a fixes their colours to the axis colours, so thickness is the only thing separating an arrow from the axis under it and cannot be given up. `lighting=False` plus 0.7 opacity makes them read as workings drawn onto the scene instead. Measured floor: below about 0.9 thickness and 0.45 opacity they disappear into the axes again. |
| 2026-09-21 | Nine of the cuboid's twelve edges are drawn, not all twelve | The three along the axes are the component arrows, and a grey dash over a coloured arrow at these line widths muddies the colour rather than reading as two things. |
| 2026-09-21 | Dashes are built as geometry, about 72 segments per box | PyVista exposes no line-stipple setting. Batched into one mesh, so a box is still a single actor. |
| 2026-09-21 | Component value labels sit four fifths along their arrow, lifted in z for x and y and pushed out sideways for z | Placed at the midpoint and nudged into two negative axes at first, which reads as no offset at all from many angles: the two displacements cancel in projection and the label lands on the origin. Near the tail all four arrows converge, so anything placed there ends up behind one of them. The axis tick numbers hang below their axis lines, so the flat labels go above. |
| 2026-09-21 | Rendering changes are now judged by rendering the scene off screen and reading the image | Three visual faults in this step were invisible from the code and from tests, and two of them the user had to report. A plain `pv.Plotter(off_screen=True)` renders the real `Scene`, `VectorActors` and `ComponentOverlays`, so the picture can be looked at before it is shown to anyone. Note the Qt-embedded `QtInteractor` cannot screenshot off screen - it raises `RenderWindowUnavailable` - and text renders as boxes off screen, so this judges geometry and colour, not labels. |

| 2026-09-22 | Components and projections are independent settings, either or both on, on the same vector or different ones | They answer different questions - what a vector is made of, and what it looks like from each side - and comparing them is what the 3D view is for. Held as two separate `str \| None` fields, so neither has to know about the other, and as two separate overlay classes for the same reason. |
| 2026-09-22 | One vector casts shadows at a time, matching components | Three shadows from two vectors would overlap on the same three planes. Same structural guard: the store holds which vector, not a set. |
| 2026-09-22 | A shadow is an arrow plus a dashed drop line from the head, in the vector's own colour | The arrow says a shadow is itself a vector; the drop line is what stops the three reading as three more vectors sharing the origin. The colour says whose shadow it is without needing a label, and keeps the axis colours free for components, so the two overlays cannot be confused when both are on. |
| 2026-09-22 | Shadows are fainter than the component arrows (0.55 thickness, 0.4 opacity against 1.3 and 0.7) | Not inconsistency. The component arrows lie on the axes and share their colours, so they need bulk to be seen at all; a shadow is in its vector's own colour, which nothing else in the scene uses, so it can be faint and still read. Both numbers were chosen by rendering and looking. |
| 2026-09-22 | No drop line where a shadow has no length | Found by the offscreen run. A vector on the z axis casts a point at the origin on the XY plane, and the drop line to it ran from the head back to the tail - a dashed copy of the vector, drawn along the vector. |
